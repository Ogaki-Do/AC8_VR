## 1. 結論と意思決定（Final Conclusion）

### ① 自前UIの独自描画・代替枠の自作：【完全断念・永久撤退】
- 過去のピッチラダー／ヨーラダー研究で得られた大原則：
  > **「UEVRで『いっそのこと自前でUIを作ってしまえ』は破綻する（同期ずれ、クリッピング、描画スレッド競合、クラッシュを招く）」**
  
  という教訓通り、カスタム枠の描画試行（未使用テキスト枠を代用した描画など）は出撃時にエラー0（ヌルポインタ参照クラッシュ）を引き起こしました。**「自力で書く機能を作ろうとすること」は完全に断念・永久封印**とします。

### ② ネイティブ四角枠（`ContainerBox`）のサイズ変更：【継続検証（v20）】
- ユーザー様の明確なご意志：
  > **「あきらめるのは自力で書く機能を作ろうとするだけ　ターゲットアイコンサイズを変更するのはあきらめねぇぞ」**
  
  に基づき、自前描画ではなく、**ゲーム本来の四角枠コンポーネント（`ContainerBox`）本体のマテリアル・シェーダーパラメータ・ビルボード要素への直接介入によるサイズ変更**に絞り込んで徹底追求します（v20テスト展開）。

### ③ 本調査で得られた「確定的な大成功成果」（本採用機能）
1. **ターゲットテキストのサイズ拡大（100%成功・完全動作）**:
   - 距離数字（`DistanceText`）、機体名（`ObjectTypeText`）、所属TGTラベル（`AllianceText`）の拡大縮小は **`UTextRenderComponent` の仕様により 100% 安定動作**。
   - 正面および360°全周で負荷ゼロ・破綻ゼロでスケール可能。
2. **JHMCS（全周360°ターゲット追従システム）（100%成功・本採用配備済み）**:
   - コックピット正面100°で消滅していた空中ターゲットを、全周360°で追従・常時表示化する `ac8_m_jhmcs.lua` を完成・本採用配備。
3. **四角枠の非表示化（100%成功）**:
   - `ContainerBox:SetHiddenInGame(true)` により、必要であれば四角枠のみを完全に消去可能であることを実証。

## 2. 検証した全手法と「できなかった理由」の技術メモ

| 試行手法 | 結果 | エンジン内部の失敗理由・技術的メカニズム |
| :--- | :---: | :--- |
| **① コンポーネントの `Scale3D` 変更**<br>(`SetRelativeScale3D`, `SetWorldScale3D`) | **変化なし** | **【ビルボードの完全スケール無視仕様】**<br>四角枠の本体 `UMaterialBillboardComponent` は、Unreal Engine C++ の `FMaterialBillboardSceneProxy` で描画されます。このプロキシはカメラ常時正対クアッドを生成する際、**トランスフォームのスケール値を内部で意図的に破棄・無視**し、内部の `Elements` のドット数だけで描画する設計になっているため。 |
| **② ルート/アクターの `Scale3D` 変更**<br>(`SetActorScale3D`, `RootComponent`) | **変化なし** | アクター全体のスケールを変更しても、親のトランスフォーム変更はビルボードに届かない（同上の理由）。テキスト部品のみ拡大される。 |
| **③ ビルボードの `AddElement` 注入** | **変化なし** | `AddElement` はビルボードに「新しい要素（Element 1）」を末尾追加する関数。既存の四角枠（Element 0）を置き換えるわけではないため、既存の四角枠は元のサイズのまま描画され続ける。 |
| **④ 動的マテリアル（MID）の変数操作**<br>(`Scale`, `Size`, `IconScale` 等) | **変化なし** | ダンプ解析により判明：四角枠のマテリアルは `MID_M_HUD_TargetContainer3DUI_000` であり、シェーダー側に外部から操作可能なサイズ関連スカラー変数が存在しなかった。 |
| **⑤ ブループリント変数操作**<br>(`BoxSize`, `TargetBoxSize` 等) | **変化なし** | ダンプ解析により判明：`ChronicleTargetContainerActorBP_C` にはコンポーネント参照しか存在せず、サイズを保持するカスタム変数は存在しない。 |
| **⑥ 親マネージャー変数操作**<br>(`LiveTargetContainerManager`) | **変化なし** | ダンプ解析により判明：マネージャー側にも全体サイズを制御する公開変数は存在しない。 |
| **⑦ 代替カスタム枠の自前描画**<br>(未使用テキストスロットによる `[ ]` 描画) | **エラー0<br>(クラッシュ)** | マップ読み込み・出撃時のアクター生成サイクルと描画更新が競合し、DirectX 12 レンダラースレッド側でヌルポインタ参照（Error 0）が発生。過去のピッチラダー検証と同様、「UEVRで自前HUD枠を作る」アプローチの限界を再確認。 |

## 3. UEVR HUD開発における確定設計原則（Golden Rules）

1. **「ビルボード（`UMaterialBillboardComponent`）のサイズは触らない」**:
   - ビルボードは表示・非表示（`SetHiddenInGame`）のみを操作対象とし、サイズの拡大縮小は試みない。
2. **「自前UIの生成・代替描画は行わない」**:
   - 「既存のものが直せないから作ってしまえ」は、描画スレッド競合やクラッシュを招くため絶対に行わない。
3. **「テキスト（`UTextRenderComponent`）は安全にスケール可能」**:
   - フォントサイズ、文字スケール、距離表示などは `RelativeScale3D` や `WorldSize` で安全・安定して操作できる。
4. **「実行タイミングはゲームスレッド（`on_post_engine_tick`）のみ」**:
   - 描画スレッド（`on_pre_slate_draw_window_render_thread`）でアクターやコンポーネントを操作すると、出撃時・マップ切り替え時にヌルポインタ参照クラッシュを引き起こす。
